# 从一个 Illustrator 小痛点，到一个可以发布的 CEP 插件

做设计文件交付时，有些问题不是“看起来很复杂”，而是“太容易被忽略”。

比如 Illustrator 里藏着几个文本框：可能在画板外，可能透明度是 0，可能字号小到肉眼几乎看不见，也可能只是复制模板时留下的占位文字。文件打开时看不出来，导出、印刷、审稿或交付时却可能出问题。

这类问题不值得每次手工翻图层，也不适合写成一段一次性的脚本。最后我把它做成了一个 Illustrator 面板插件：**Text Frame Inspector**。

它做的事情很简单：扫描当前文档里的所有文本框，识别风险文本，列出结果，点击就定位，高亮所有文本框，或者只高亮敏感/占位文本框。真正花时间的地方，不只是功能本身，而是怎么把它从“自己能用”变成“别人拿到也能装、能用、能发布”的插件。

这篇文章记录这个过程。

## 需求其实很朴素：把容易漏掉的文本框找出来

Illustrator 文件里，文本框不一定都是显眼的正文。

交付前最容易出问题的文本对象大概有几类：

- 画板外的文本框
- 空文本框
- 透明度为 0 的文本
- 隐藏图层上的文本
- 极小字号文本
- 模板里残留的占位文本

中文模板里经常能看到类似 `滚滚长江东逝水`、`是非成败转头空` 这样的占位开头。英文环境里也一样，只是换成 `lorem ipsum`、`placeholder`、`dummy text`、`sample text`、`the quick brown fox`、`your text here` 这类内容。

所以这个插件的第一版规则很明确：

- 扫描 `app.activeDocument.textFrames`
- 按前缀判断占位文本
- 检查空内容、透明度、隐藏图层、极小字号、画板外位置
- 把结果返回给面板
- 在面板里展示列表
- 点击列表项时，在 Illustrator 里选中并定位对象

这不是一个很大的需求，但它很适合做成工具。因为它解决的是重复劳动，而且每次检查都应该稳定、可见、可追溯。

## 如何安装和使用

如果只是作为用户使用，不需要理解 CEP、ZXP 或 ExtendScript。最简单的方式是下载发布页里的安装包。

我给这个插件准备了三种交付物：

- `TextFrameInspector-Setup-1.0.0.exe`
- `TextFrameInspector-1.0.0.zxp`
- `TextFrameInspector-1.0.0.zip`

对 Windows 用户来说，最推荐的是 `.exe` 安装包。下载后双击运行，它会自动把插件安装到当前用户的 Adobe CEP 扩展目录。

安装完成后，如果 Illustrator 正在运行，先完全退出 Illustrator，再重新打开。然后在菜单里找到：

```text
窗口 > 扩展（旧版） > Text Frame Inspector
```

如果你的 Illustrator 是英文界面，入口通常是：

```text
Window > Extensions (Legacy) > Text Frame Inspector
```

打开面板后，日常使用流程很简单：

1. 打开一个 Illustrator 文档。
2. 点击 `扫描所有文字`，插件会扫描当前文档里的全部文本框。
3. 查看下方列表，红色标记的是风险项。
4. 如果列表太长，可以在搜索框里输入关键词，只过滤包含该内容的文本框。
5. 点击搜索框右侧的 `⚠` 按钮，可以只看风险项，也就是占位文本、空文本、透明文本等被筛出来的问题对象。
6. 点击列表里的某一项，插件会在画板中选中并定位到对应文本框。
7. 点击 `高亮所有文本框位置`，可以给所有文本框画临时定位框。
8. 点击 `高亮所有敏感字文本框`，只给风险文本框画红色定位框。
9. 检查完成后，点击 `还原`，插件会删除临时高亮图层。

如果你想调整检查规则，可以切到 `配置` 页面。这里可以修改敏感词前缀、颜色和线框粗细。比如你们团队的模板里还有其他固定占位文案，就可以一行一个加进去。保存后，下次扫描和高亮都会按新的配置生效。

`.zxp` 更适合 Adobe 插件生态或 ZXP 安装器用户；`.zip` 则是备用方案，适合手动复制安装。手动安装时，需要把解压后的 `TextFrameInspector` 文件夹放到：

```text
C:\Users\<你的用户名>\AppData\Roaming\Adobe\CEP\extensions\
```

最终路径应该类似：

```text
C:\Users\<你的用户名>\AppData\Roaming\Adobe\CEP\extensions\TextFrameInspector\
```

这种方式更偏开发者或高级用户。普通用户优先用 `.exe` 安装包就够了。

## 为什么不是单文件脚本，也不是 `.aip`

一开始很容易把 Illustrator 插件理解成三种东西：

- `.jsx` 脚本
- `.aip` 原生插件
- CEP/UXP 面板插件

这个项目最后选择的是 **CEP 面板插件**。

原因很现实。

`.jsx` 适合一次性执行任务，但不适合做长期打开的面板。它可以扫描，也可以弹窗，但很难提供一个稳定的结果列表、配置页、搜索框和持续交互。

`.aip` 是 Illustrator 原生插件格式，通常要用 C/C++ 开发。这个功能没有必要走到那一步，开发成本、调试成本和分发成本都太高。

CEP 面板刚好卡在中间：前端可以用 HTML、CSS、JavaScript 做界面，Illustrator 内部逻辑可以用 ExtendScript 调 API。它不是最新潮的方案，但对这种小型生产工具来说，足够直接。

最终项目结构大概是这样：

```text
TextFrameInspector/
  CSXS/manifest.xml
  index.html
  css/style.css
  js/CSInterface.js
  js/main.js
  jsx/host.jsx
```

`manifest.xml` 告诉 Illustrator 这是一个 CEP 面板，宿主是 `ILST`。面板 UI 跑在内嵌浏览器里，真正访问 Illustrator 文档的是 `host.jsx`。

前端通过：

```js
cs.evalScript('getAllTextFrames()', callback)
```

调用 Illustrator 侧函数。ExtendScript 扫描完文本框后，把 JSON 字符串返回给面板，面板再渲染列表。

这就是整个插件的主通信链路。

## 高亮不是修改原对象，而是画临时标记层

最开始我尝试过直接给文本框加描边。这个做法看起来简单，但不理想。

一方面，文字对象本身的描边不一定明显。缩放比例小、画板内容复杂时，用户仍然看不清。另一方面，直接修改原始对象也会让人不放心：工具只是检查文件，不应该污染作品。

所以后面改成了临时图层方案。

插件会创建一个临时图层：

```text
__TextFrameInspector__
```

高亮时，不改原始文本框，而是在这个图层上画矩形框和定位线。点击某个结果项时，会画一个定位框，再加横向和纵向的坐标线。这样视觉上更接近“定位工具”，而不是简单给文字加样式。

还原也很干净：删除这个临时图层即可。

这个设计对用户心理很重要。检查工具如果让人担心会改坏文件，用户就不敢用。把所有高亮都放到临时层里，边界更清楚。

## 配置页和中英文默认规则

后来又加了配置页。

原因是占位文本没有统一标准。不同团队、不同模板、不同语言环境，都会有自己的默认文字。

现在配置页支持：

- 敏感词前缀，每行一个
- 全部文本框高亮颜色
- 风险文本框高亮颜色
- 定位线颜色
- 各类线框粗细

默认规则里同时放了中文和英文：

```text
滚滚
滚滚长江东逝水
是非
是非成败转头空
lorem
lorem ipsum
placeholder
dummy text
sample text
the quick brown fox
your text here
text goes here
```

面板 UI 也做了中文/英文切换，默认中文。这样它不只是一个给自己用的小工具，也更接近可以发给别人用的产品。

## 真正麻烦的是发布格式

功能跑通之后，另一个问题出现了：怎么发给别人？

CEP 插件本质上是一个文件夹。开发时放到：

```text
C:\Users\<username>\AppData\Roaming\Adobe\CEP\extensions\
```

这对开发者没问题，但对普通用户很乱。

所以最后准备了三种产物：

- `zip`
- `exe`
- `zxp`

这三种不是重复，而是面向不同场景。

`zip` 是最简单的备用方案。用户解压后复制文件夹即可。它不优雅，但透明、稳定、容易排查。

`exe` 是面向 Windows 用户最友好的交付形式。用户双击安装器，安装器负责把 CEP 文件夹复制到正确位置。很多淘宝店、工具店看起来像“单文件插件”，底层经常就是这种安装器包装。

`zxp` 是 CEP 插件更正式的包格式，适合 Adobe 生态分发、ZXP 安装器，以及后续尝试 Adobe Developer Distribution。

这里有一个关键判断：

> GitHub Actions 不能把插件变成某种高级格式，它只能自动执行打包流程。

插件格式由项目类型决定。这个项目是 CEP，所以合理的发布结果就是 CEP 文件夹、ZXP 包，或者套一层 Windows 安装器。

## GitHub Actions 为什么要用 tag 触发

我不希望每次 push 代码都生成安装包。因为普通 push 可能只是改 README、修文案、调样式，不一定是正式版本。

所以 workflow 写成只在 tag 推送时触发：

```yaml
on:
  push:
    tags:
      - "v*"
```

也就是说：

```powershell
git push origin main
```

只上传代码，不发版。

真正发版要这样：

```powershell
git tag v1.0.0
git push origin v1.0.0
```

这时 GitHub Actions 才会生成：

```text
TextFrameInspector-1.0.0.zip
TextFrameInspector-Setup-1.0.0.exe
TextFrameInspector-1.0.0.zxp
```

这个流程有个好处：版本号和产物绑定。看到 `v1.0.0`，就知道对应的安装包是哪一次代码生成的。

中间也踩过一个坑：下载 `ZXPSignCmd.exe` 时路径写成了 `win64`，结果 GitHub 返回的是 404 HTML 页面，不是可执行文件。修复后改成了 Adobe CEP Resources 里的 `x64` 路径，并加了文件大小检查，避免以后再把 HTML 当工具下载。

这种问题很典型：发布脚本不能只“看起来能跑”，还要校验关键产物是不是正确的文件。

## 能不能上 Adobe 插件市场

可以尝试，但不能简单理解为“有 zxp 就一定能上”。

Adobe 现在通过 Developer Distribution 管理 UXP 和 ZXP 插件分发。对 CEP 插件来说，`zxp` 是更正式的包格式。要走 Adobe 市场，除了包本身，还要准备：

- 插件名称和英文简介
- 详细功能说明
- 图标
- 截图
- 兼容版本说明
- 隐私说明
- 支持地址
- 版本号和平台信息
- 审核需要的其他材料

所以现在这个项目的状态是：技术上已经朝 Adobe 分发需要的形态靠近了，但真正上架还需要补市场素材和审核材料。

我不会说它一定能过审。更准确的说法是：它已经从“本地插件文件夹”走到了“可以生成 ZXP、可以准备提交”的阶段。

## 小工具产品化，重点不只是代码

回头看这个过程，插件功能本身并不复杂。

复杂的是把它变成一个别人也能使用的东西：

- 要选对插件形态
- 要有稳定的安装方式
- 要有清楚的 README
- 要有中英文说明
- 要有版本号
- 要有可复现的打包流程
- 要知道 GitHub Actions 什么时候触发
- 要知道 Adobe 市场需要什么

很多小工具停在“我这里能跑”。但只要想发给别人，就会进入另一个阶段：交付、安装、版本、文档、审核、兼容性。

Text Frame Inspector 这个项目最大的价值，可能不是它扫描了多少个文本框，而是它把一个很小的 Illustrator 检查需求，推到了一个可以发布的插件形态。

对我来说，这才是从脚本到产品的分界线。
